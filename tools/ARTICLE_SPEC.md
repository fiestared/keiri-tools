# 記事の書き方（keiri-tools コラム）

**このファイルが記事の正本の型。** `node tests/test_article_structure.mjs` が機械で強制する。
書き終えたら必ず自分で流し、緑にしてから終わること。

## 0. テーマを決める（着手前に必ず。ここを飛ばすと書いた後に捨てることになる）

**書き始める前に `python3 tools/keyword_demand.py "<主題語>" "<言い換え>"` を打つ。**
この道具は需要（月間検索数）と**自サイトの被覆**を同時に出す。出力の最後に
「新規に書かず、既存記事を深く書き直すことを検討する(重複記事は検索で互いを食い合う)」と
出たら、その警告に従って判断すること。

🚫 **h1／title の grep だけで「空白」と判定しない。**
既存記事が**h2の節として**その主題を持っていることがあり、grep では見えない。

> **実例（2026-08-19）**: 「税抜経理」「税込経理」を title/h1 に持つページは全274ページで0
> だったので新規作成に着手した。書き上げてから `keyword_demand.py` を打ったところ、
> **3記事が節として保有**していた —— `karibaraikin-kariukekin`（h1に「控除対象外消費税は
> 60ヶ月で落とす」・h2に「繰延消費税額等は60ヶ月・初年度は半分」）、`kosaihi-kaigihi-chigai`
> （h2「税抜経理か税込経理かで1万円判定が動く」）、そして `shogaku-genka-shokyaku` は
> **同じ国税庁No.5403質疑応答の、同じ107,800円のパソコンの設例**を既に持っていた。
> 記事のリードの目玉がまるごと重複していた。書き直して救ったが、着手前に1コマンド打てば
> 済んだ。**道具は存在していた。打たなかっただけ。**

🚫 **需要を最後に測らない。** 上の実例では需要は「税抜経理」260/月で、同じ日の他の候補
（生前贈与 32,400／印紙税 14,480／在職老齢年金 11,840）より**2桁小さかった**。
★**「サイトが持っていない主題」を空白と呼ぶ前に需要を測る。持っていない理由が
「需要が無いから」のことがある。**

判定の順序はこの3つ。順番を入れ替えない:

1. **需要を測る** → 候補が複数あるなら大きい方から取る
2. **被覆を測る**（`keyword_demand.py` の重複チェック。h1だけでなく節まで見る）
3. **重なっていたら決める** → ①既存記事を深く書き直す（推奨）②役割を分けて
   重複部分をリンクで譲る ③やめる。**重なったまま書き上げない**

## 絶対に守ること（これを破ると商品が壊れる）

1. **数字を推測で書かない。** 税率・料率・上限額・期限は、必ず**一次情報**（国税庁・
   日本年金機構・全国健康保険協会・厚生労働省・e-Gov法令）を読んで確かめる。
   確かめられなかった数字は**書かない**。「たぶんこうだったはず」は、経理の現場では実害になる。

   ⚠️ **政府サイトの数値確認に WebFetch を使うな。要約器が「もっともらしい嘘」を返す。**
   実例2件（2026-07-13）: ①国税庁の2割特例のページで、対象者を「認定経営革新等支援機関の支援を
   受けた小規模事業者」と**完全に捏造**。②協会けんぽの料率ページで「最低は沖縄県9.44%」と回答
   （正しくは新潟県9.21%。同じ回答の中に9.21%を列挙しながら矛盾していた）。
   **エラーにならないので気づけない。必ず生テキストを読む。**
   ```
   curl -s <URL> | grep -io 'charset=[a-z0-9_-]*'  # ★まず文字コードを見る。ディレクトリで決め打つな
   curl -s <URL>                                   # charset=utf-8 のとき(iconv を通すと壊れる)
   curl -s <URL> | iconv -f cp932 -t utf-8         # charset=shift_jis のとき
   # 同じ taxanswer 配下でも混在する: 1130.htm=UTF-8 / 1130_qa.htm(質疑応答)=Shift_JIS
   curl -s -o /tmp/x.pdf <URL> && pdftotext -layout /tmp/x.pdf -
   curl -s "https://laws.e-gov.go.jp/api/2/law_data/{law_id}"      # ← v2。v1は古い条文を返す
   ```
   **未施行リビジョンに注意**: 令和8年度改正の所得税法は**施行日が令和8年12月1日**。
   今日の「現行」を引くと**改正前の額が返る**。`/api/2/law_revisions/{law_id}` で将来施行版を読む。

   🔴 **これは所得税法だけの話ではない。租税特別措置法も同じ日に入れ替わる。**
   しかも措置法は**条番号そのものが別の制度に付け替わる**ので、番号で引くと
   「条文はあるのに中身が違う」という、いちばん気づきにくい外し方をする。
   実測（2026-08-19 第4便・e-Gov API v2 で両リビジョンを取得して比較）:

   | 条番号 | 令和8年11月30日まで（現行） | 令和8年12月1日から |
   |---|---|---|
   | 措置法29条の4 | 退職勤労者が弁済を受ける未払賃金に係る課税の特例 | **給与所得控除の最低控除額等の特例（74万円）** |
   | 措置法41条の16の2 | 「令和七年分以後」…加算 37/30/10/5万の**4段** | 「令和八年分以後」…489万以下**42万**・超5万の**2段** |

   ★**この便は実際にこれで誤診しかけた。** 前便が記録した「基礎控除104万円＝62万＋42万」を
   検算しようとして*現行*の41条の16の2を引き、加算が37万だったので
   「62+37=99万。前便は誤り」と結論しかけた。**正しかったのは前便で、間違っていたのは
   引いたリビジョンの方**だった（12/1施行版の加算が42万）。
   ✅ **令和8年分の税額に関わる条文を引くときは、必ず 20261201 のリビジョンIDを名指しする。**
   ✅ **条文をメモするときは「条番号」ではなく「見出し＋施行日」で控える。**
   番号だけのメモは、半年後に開くと別の制度を指している（申し送り873の一般形）。
   PDFの**表**は `pdftotext` だと結合セルで行がずれる。**`pdfplumber` でbboxごと**取ること。
   **改正直後は国税庁のタックスアンサーが古いままのことがある。財務省の大綱が正本。**

   🔴 **条文の「号数」を目で数えない**（2026-08-19 第5便で実害）。
   記事に「財務諸表等規則17条は12項目・49条は14項目」と書いたが、正しくは**13と15**だった。
   飛ばしていたのは**枝番号**（三の二・七の二）。改正で号を挿し込むとき既存の号数を
   動かさないのが立法の作法なので、**改正が入った条ほど枝番号を持つ＝実務で重要な条ほど
   目視で数え間違える。** 正規表現で本文から拾うのも誤り（本文中の「一年内」等を拾って水増しする）。
   ✅ **`python3 tools/egov_elm.py <law.json> --items <条番号> [--para N]`** を打つ。
   木構造（Article > Paragraph > Item）から数えるので枝番号も正確。`tests/test_egov_item_count.mjs` が固定。

   🔴 **条文を引用するなら `<blockquote>` に置く。表やリストに置くと照合されない**
   （2026-08-19 第6便で実害）。`check_quotes.py` の逐語照合は **blockquote だけ**を見る。
   売上原価の記事で財規75条1項1号を「商品又は製品の期首棚卸高」と書き、**「条文の項目」という
   見出しの表**に置いた。条文の実物は「商品又は製品**（半製品、副産物、作業くず等を含む。
   以下この項及び次条において同じ。）**の期首棚卸高」で、**括弧書きが語の途中に入る**。
   ★号数の枝番号と同じで、**目は括弧書きを飛ばす。** 逐語のつもりなら括弧書きごと写し、
   要約なら「条文」と名乗らない（省略するなら「……」で明示する）。
   ✅ `check_quotes.py` が ③ として**候補**を挙げる。⚠️ 実測は真陽性1に対し候補10なので
   **exit code には影響しない**。目で見て判断すること。

   🔴 **`<blockquote>` には条文本文だけを入れる。出典ラベルを同居させない**
   （2026-08-20 第10便で実害）。`check_quotes.py` は blockquote の中身を**丸ごと1断片**として
   照合するので、`<blockquote>労働基準法109条<br>使用者は…</blockquote>` のように親切なつもりで
   ラベルを入れると、**そのラベルの分だけ必ず不一致になる**（21件中5件が落ちた）。
   ✅ 出典は**直前の地の文**で名乗る（「受けた施行規則54条1項が、次の8つの号を挙げます。」）。
   ★一般形: **検査を持つ構造物を書くときは、その検査を通っている既存記事を1つ開いてから書く。**
   記法を発明する前に `docs/column/genkin-suitocho-kakikata/` の blockquote を見れば5分で済んだ。

   🔴 **引用を入れ子にしない。「」の中に「」が要るなら、そこは引用をやめて地の文に割る**
   （2026-08-20 第10便）。附則143条1項を全文引用しようとして
   「…同条中『五年間』とあるのは、『三年間』とする」と書き、**内側の括弧を「」から『』へ
   書き換えていた**＝非逐語。正しくは内側だけを短く引く
   （「109条中の「五年間」を当分の間「三年間」と読み替えている」）。
   ★**これは4便連続で出ている癖の一般形**（第7便「二月」→「2月」／第8便「五日以内」→「5日以内」／
   第9便 算用数字＋動詞の短縮／第10便 括弧記号）。顔は毎回違うが、正体はどれも
   **「鉤括弧の中身に手を入れてしまう」**こと。地の文の鉤括弧も**全数**コーパスに当てて確かめる。

   ✅ **その全数照合は `check_quotes.py` の ④ が自動でやる**（2026-08-20 第11便で道具化）。
   手で書き捨てスクリプトを書かないこと —— **第7〜11便の5回連続で手書きしており**、
   このファイル自身が戒めている「毎回ゼロから書き直され、毎回ちがうバグで壊れた」状態が
   blockquote の外側にだけ残っていた。④ は blockquote を除いた地の文の「…」『…』を全部拾い、
   コーパスに無いものを出す。**★印が付くのは「条文の逐語を名乗っていそうなもの」だけ**で、
   判定は ①20字以上 ②文語の目印を含む ③**near-miss＝軽い正規化（算用数字→漢数字・
   『』→「」・および→及び 等）で当たるようになる**、のどれか。③が単独で効くのが要点で、
   第11便の「帳簿および請求書等」（9字・目印なし）は③だけが拾った。
   ⚠️ ③④は **candidate であって gate ではない**（exit code に影響しない）。地の文の鉤括弧は
   大半が筆者自身の言葉なので、gate にすると毎回赤くなり検査を無効化する圧力になる。
   実測（第11便の記事）: 鉤括弧40種のうち MISS 21件、★は2件まで絞られた。

   🔴 **通達は e-Gov に無い。`tools/fetch_tsutatsu.py` でコーパスを作ってから照合する**
   （2026-08-19 第7便で道具化）。それまで通達の照合だけが毎便 /tmp の書き捨てに戻っており、
   `check_quotes.py` の docstring が戒めている「毎回ゼロから書き直され、毎回ちがうバグで壊れた」
   状態が**通達側にだけ残っていた**。
   ```
   python3 tools/fetch_tsutatsu.py 02_02_01 02_02_02 05_01_01 05_01_02 05_03 -o /tmp/t.json
   python3 tools/check_quotes.py <article.html> --law /tmp/t.json --law /tmp/<egov条文>.json
   ```
   ⚠️ **国税庁は存在しないページにも HTTP 200 で「指定されたページを表示できませんでした」を返す。**
      道具が1ページ200字未満で fail-closed に落とす（🚫 200 をページが取れた証拠にしない）。
   ⚠️ **10,000字（`MIN_CORPUS_CHARS`）を通すためにページを足さない。**
      実測: 法人税基本通達の第5章は全節を足しても 8,530字しかない。閾値は「抽出が壊れて空を返した」
      を捕まえるためのもので、通達ではその役目を**1ページごとの字数チェック**が果たす。
      足すなら「**記事が実際に引く通達だから**」という理由で足すこと。
   ★条文と通達を**同時に**渡してよい（合成コーパスで照合する）。片方だけだと、もう片方の引用が
      全部「不一致」に見える。逆に e-Gov 側だけを渡すとコーパスが小さすぎて**測定不能**になる
      （実測: 施行令32条だけだと 1,160字で fail-closed）。

2. **出典を h2「出典」に列挙する。** どのページを見たか（発行元＋資料名）を書く。
3. **年度・年分を明記する。** 「令和8年度」「令和8年分」。無記名の数字は将来の嘘になる。
4. 一般論の免責を末尾に置く（既存記事の最終行と同じ文言）。
5. 🔴 **主張の台帳を作り、`node tools/check_claims.mjs --changed` を緑にしてから commit する**（2026-09-28 新設）。
   書いた（足した）数字・年度・日付を全部、**一次資料の逐語つき**で `claims/<ページ>.json` に載せる。ひな形は `claims/_TEMPLATE.json`。
   「原則」「常に」「必ず」「一律」などの言い切りは、1回ごとに**原則の外を確かめた記録**を absolutes に書く。計算機のページは公表例・境界値の tool_cases を2件以上。
   ★理由: 記事レビューを8周回したら、主張の約7%が誤りだった（書く時点で主張を1件ずつ照らしていなかった）。
   誤りの型と書く前のチェックリストは gbrain `keiri-tools/article-error-patterns`。**書く前に読む。**

## ファイルの場所

`docs/column/<slug>/index.html` の1ファイルだけを作る。

🔴 **相対パスで `mkdir` しない。必ず絶対パスで作る**（2026-08-20 第12便で実害）。
Bash の作業ディレクトリは `cd /tmp` を挟むと **`~/Scripts` に戻される**ことがあり、
そのまま `mkdir -p docs/column/<slug>` を打つと **`~/Scripts/docs/column/<slug>/`**
という repo の外に記事ができる。テストも生成器も repo の中しか見ないので、
**何も警告が出ないまま「書いたはずの記事が無い」状態**になる。
★これは**初犯ではない**: 掃除のとき `~/Scripts/docs/column/mitsumorisho-kakikata/` という
**空ディレクトリが既に在った**＝過去の便が同じ所で滑って、痕跡だけ残していた。
✅ `mkdir -p /Users/masahiroyasu/Scripts/keiri-tools/docs/column/<slug>` と絶対で打つ。
✅ 記事を書いたら `git status --short` に **`A docs/column/<slug>/index.html` が出ることを確かめる**
   （出ないなら repo の外に書いている）。
**sitemap.xml / column/index.html / assets/style.css は触らない**（親が中央で更新する。競合するため）。

## 書き終えたら流す生成器（順序つき。ここが抜けるとテストが赤くなる）

記事の HTML を書き、`gen_index_sitemap.mjs` の `ORDER` と `CATEGORIES` に slug を登録したら、
**この順で流す**。最後に `node tools/run_tests.mjs` を緑にしてから終わる。

```
node tools/gen_faq_jsonld.mjs      # h2#faq の Q/A から FAQPage を焼く
node tools/gen_qa_index.mjs        # ★docs/assets/qa_index.json。FAQを持つ記事を足したら必須
node tools/gen_tool_related.mjs    # 関連リンク（他ページ側にも被リンクが入る）
node tools/gen_ogp.mjs             # og:title/og:description（title を触ったときも必要）
node tools/gen_x_share.mjs && node tools/gen_x_link.mjs
node tools/gen_datemodified.mjs    # dateModified を git 履歴から焼く
node tools/gen_index_sitemap.mjs   # ★下記のとおり --check が緑になるまで繰り返す
```

🔴 **`gen_qa_index.mjs` を忘れやすい。** FAQ を持つ記事を足すと `tests/test_qa.mjs` が
`gen_qa_index.mjs --check` で落ちる。他の生成器と違って**記事側の HTML を書き換えない**ので、
「HTML に差分が出ないから流さなくてよい」と誤解しやすい。実際に忘れて赤にした（2026-08-20）。

🔴 **`gen_index_sitemap.mjs` は「最後に1回」ではない。** `--check` が緑になるまで回す。
sitemap の実行自体が `docs/column/index.html` を書き換えるので**2周目が要る**し、
そのあとに `docs/**.html` を触る生成器を1つでも動かしたら**やり直し**になる。

⚠️ **`gen_datemodified.mjs` の差分は、原因を作った回では出せない。** HTML の日付を **git の履歴**と
突き合わせる検査なので、commit 前は古い日付どうしで一致してしまう。
＝ **前回のコミットが触ったファイルの分が、次に記事を書くときに出てくる**のが正常。
🚫 「前回テストが緑だった」を「前回に問題が無かった」の根拠にしない。

## 型（テストが見ている）

```
<head>
  <title>…</title>                     60字以内。検索結果で切れる
  <meta name="description" …>          60字以上。要点＋数字を入れる
  <link rel="stylesheet" href="../../assets/style.css">
  <link rel="canonical" href="https://keiri-tools.com/column/<slug>/">
  JSON-LD @graph に Article（datePublished/dateModified）と BreadcrumbList
  GA4タグ (G-E742DSDHPD) と AdSense (ca-pub-2635067516563578)
     → 既存記事の <head> をそのままコピーして中身だけ差し替えるのが確実
</head>
<body>
  <header class="site">…共通ナビ…</header>
  <main>
  <nav class="breadcrumb">ホーム › コラム › <この記事></nav>
  <article>
    <h1>…</h1>
    <p class="article-meta">公開日: 2026年7月13日</p>
       ← 日付行は**公開日・更新日だけ**（2026-09-30〜。test_article_structure が落とす）。
         根拠の出所・確かめ方・訂正の記録は、末尾の h2「出典」の直後に
         <p class="source-method">〜の条文（e-Gov法令検索）で確認して作成。</p> として1回だけ書く。
         「API v2」「保存条文」「木構造から機械的に」「今回の資料」のような作業記録の言葉は読者に見せない
    <p class="byline">文責: <a href="../../about/">Masahiro Yasu</a>（クリニック・EC事業の経営者／経理実務者）</p>
       ← 実名バイライン必須(E-E-A-T)。JSON-LDの author も Person(Masahiro Yasu, about参照)で書く。
         匿名Organizationに戻すとテストが落とす。免責(税理士でない旨)はaboutと記事末尾の注記に集約し、
         バイラインには書かない(毎回書くと冗長・防御的)。本文は「あなたはこうすべき」でなく
         「一般に〜と計算する」で書く(一般的情報提供であって個別の税務相談ではない=税理士法の線引き)

    〈結論ファーストのリード 2〜3段落〉  ← 読者は「答え」を探しに来ている。先に言う

    <nav class="toc"><div class="toc-title">目次</div><ol>…全h2へのリンク…</ol></nav>

    <h2 id="…">…</h2>   ← h2 は3つ以上。すべて id を持ち、すべて目次に載る
    …
    <figure class="figure">…インラインSVG…<figcaption>…</figcaption></figure>
       ← 図解は必須。外部画像は使わない（<img src="http…"> はテストが落とす）
```

`.tool-grid`＋`.tool-card`（関連カード）・`.summary-box`・`.note`・`.scroll-wrap`（横長の表を包む）・

## 中身の質（ここで差がつく）

- **結論を先に。** 「〜については諸説あり」ではなく「**結論から言うと、Xです**」。
- **具体例と実数を必ず入れる。** 「東京都・月給30万円・35歳なら、健康保険料は◯◯円」。
  抽象論だけの記事は誰にも読まれないし、上位に来ない。
- **落とし穴・間違えやすい点を書く。** 実務者は「自分のケースは大丈夫か」を確かめに来る。
  1日違いで結論が変わる／年度で変わった／例外がある、を明示する。
- **表で比較する。** 「AとBの違い」は文章で並べず表にする。
- 競合（会計SaaSのブログ）が書いていない **踏み込んだ一段**を必ず1つ入れる。
  改正の経緯・条文番号・境界ケース・実際の帳票の見方など。
- **文字数の目安 8,000〜12,000字（可視テキスト）。薄い記事は量産しても価値がない。**

  🔴 **2026-08-23 第4便で実測に基づき改訂した（旧「3,000〜6,000字」は実態と合っていなかった）。**
  旧目安のままだと**毎便「目安の2倍」という誤った超過報告が出続ける**し、
  悪くすると**実際に効いている記事より薄いものを書く圧力**になる。実測は次のとおり:

  | | 実測 |
  |---|---|
  | 全241記事の可視字数 中央値 | **9,809字**（平均 9,893・p25 8,050・p75 12,231） |
  | 旧目安 3,000〜6,000字に収まる本数 | **23/241 ＝ 10%** |
  | 6,000字超 | **210/241 ＝ 87%** |
  | Bingクリック上位9ページの中央値 | **9,387字**（3,000〜6,000に収まるのは 1/9 だけ） |

  ★**上位ページも中央値も揃って9,000字台**なので、「長いから伸びていない」ではない。
  旧数字は初期の数十本の実態を写したもので、そこから母集合が入れ替わったのに更新されていなかった。
  🚫 **この幅を下限として使わない。** 短くても主題が薄くなければよい（実測 p10 は 4,351字）。
  上限側も同じで、12,000字を超えたら**削る前に「重複していないか」を見る**（長さ自体は欠陥ではない）。
  ★次にこの数字を疑うときも、**意見ではなく全記事を数え直して**決めること。

## SVG図解の作り方

`viewBox` を切って、矩形・線・テキストで描く。凝った絵はいらない。
**流れ図（判定の分岐）・時系列（いつ何をするか）・内訳（金額の内わけ）**のどれかが有効。
色は `var(--accent)` `var(--sub)` `var(--warn-line)` などCSS変数が使える。
文字は `font-size="13"` 程度、`fill="currentColor"` で本文色に追従させる。

## 表示の規則（2026-10-08・内容修正が UI/UX の修正を戻した回帰から）
- ツールの h1 の直後（日付行の次）に注意（`.note`・`.callout`）を置かない。注意は結果欄の下か、該当する入力欄の details の中へ。表の1行の中で同じ条件を複数のセルに書かない（区分名のセルに `.cell-note` で1回、または表の下の※1行）。未確認の注記は表ごとに※1行と調査方法の1回だけ。
- 読者に見える文（本文・出典・title・description）に作業記録の語（「API v2」「法令ID」「今回の資料」「機械的に」「…に基づいて作成」「実読」「木構造」）を書かない。出典は「e-Gov法令検索『○○法』△条」の形。`node tests/test_ux_content_regressions.mjs` が落とす（既存ページの件数は上限として固定）。

## 空の表示枠を出さない（2026-09-27）

注意・エラー・結果の器は空のまま枠や背景を見せない。関連記事が0件なら見出し・sectionも生成しない。非表示の子、見出しだけの結果、コピー操作だけの結果、TODO・ダッシュだけの仮置きも完成扱いにしない。既存の生成器の後に `node tools/gen_presentation_markup.mjs` を実行する。本文の数値表記は表示の都合で書き換えない。

`./run_tests.sh` は新ページも自動列挙し、実ブラウザで空の枠を検査する。計算機は正常入力のE2Eシーンを登録し、計算→不正入力→入力クリア→再計算の検査を通す。例外をページ単位で除外しない。要素例外が必要ならセレクタ・表示上の理由・壊し検査をセットで記録する。


## 数字を書く文には、その数字の条件を同じ文に書く（2026-10-04・Masahiro「すぐにどちらとも入れて」）
- 照合（theme_round の単位モード）は**1文ずつ、その文だけで正しいか**を見る。台帳や別の段落に条件が書いてあっても、その文に無ければ指摘される。
  2026-10-04 実測: 執筆便の1周目の指摘の6〜8割が「条件・限定の抜け」（数字の誤りは2〜6件）で、修正が10周かかった。
- 数字（金額・率・人数・期限）を書く文には、その数字の**年分・対象者・上限や範囲**を同じ文に書く。
- 冒頭・見出し・表のセル・図・FAQ・まとめで**同じ数字を条件なしに言い換えて繰り返さない**。繰り返すなら条件ごと書く。条件を書けない場所（見出し・短いセル）には数字を置かない。
- 台帳の各主張に `must_with`（その数字と同じ文に必ず書く語）を書き、`node tools/check_claim_scope.mjs <page>` が 0 件になるまで直してから照合に出す。

## 自分で計算した数字は、計算して確かめる・言い切らない（2026-10-05）
- 2026-10-03〜04 の執筆便の high 608件で多かったのは、①書き手が計算した境界・差額・設例の数字の誤り（例: 最低保障額が効く上限を「約203万円」と書いたが式からは約196万6,667円）と、②例外がある主張の言い切り（「全域で5万円下がる」「各帯の起点で計算した値」）。
- 正本に書いてある数字を使う。自分で計算した数字（境界・差額・年収別の設例・税額）を書くなら、台帳で `derived: true` にし、`calc` に計算式と**実際に計算した実行結果**を書く（暗算・手計算の数字を書かない）。
- 「全域」「すべての」「各〜」「いずれも」「必ず」「常に」「一律」を数字の文に使うときは、例外が本当に無いかを正本の同じ条・表・注で確かめる。`check_claim_scope.mjs` が該当する文を△で一覧に出す。

## 数字ごとに書く条件の型（2026-10-05・国民年金保険料の記事の high 34件から）
- **金額は「どの期間の・どの払い方の・誰の」額か**を同じ文に書く（例: 2年前納の割引額は「4月から始める24か月分を現金・クレジットカードで納める場合」）。
- **期限は休日の扱い**を書く（土日祝・年末年始なら翌営業日／前営業日）。延滞金・加算金は「かからない例外」があれば書くか「主な例外は…」と示す。
- **法令の算式で決まる額は端数処理まで**書く（「17,000円×改定率」だけでは 17,918円になり、実額 17,920円とずれる）。
- 台帳の、数字を含む主張には `must_with` を必ず書く（`check_claim_scope.mjs` が checked 2026-10-05 以後の台帳で必須にした）。

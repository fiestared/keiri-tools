# Rendered layout gate

`./run_tests.sh` includes `test_layout_markup`, `test_layout_render`, `test_layout_mutations`, and `test_layout_visual`. A missing browser/dependency/baseline fails; there is no skip switch. Install jsdom as required by the existing tests. Playwright is resolved locally, then from `PLAYWRIGHT_PATH`, then `~/Scripts/accounting/node_modules/playwright/index.js` (the project's existing browser installation). Chromium must be installed for that Playwright version.

## Geometry and behavior

Every `docs/**/index.html`, including embeds, is discovered on every run. Each opens in Chromium at 1280×900 and 390×900, DPR 1. The test starts its own loopback Python http.server, waits for network idle/fonts/two frames, and requires a successful response and exactly one measurement per page/width. Four tabs keep the 510-page audit practical. External requests, including analytics and ads, are blocked; ad markup is not modified. Browser page errors fail as well. This checks the default rendered state, not every possible calculator result or third-party ad creative.

Failures cover page horizontal overflow; empty visible headings; duplicate element IDs; misaligned sibling inputs; help between an individual label and control or above its described control; absent table borders/background; number+unit line splits in numeric cells; explicit numeric column alignment; SVG text outside viewBox/rect or overlapping text; broken local images and accidental image clipping; hidden-overflow text clipping and overlapping adjacent text blocks; body/footer left-edge mismatch; missing Q/A markers or answer emphasis overriding normal weight; and missing TOC on multi-section calculator pages.

SVG text uses `getBBox()` and transformed corners in the root SVG coordinate space. The containing rect is the smallest rect enclosing the text center; this is an inference, not a full diagram semantics parser. Authors must actually inspect diagrams, including labels fully detached from their intended boxes, text/path collisions, line balance and readability. Quantitative bars/timeline bands may carry `data-layout-role="bar"` **and an explanatory `data-layout-note`** after visual review. This exempts only the rect-as-text-container inference; viewBox/text-overlap checks remain active. Do not mark ordinary flowchart boxes as bars. No page is allowlisted.

Legitimate exceptions: local table overflow stays scrollable; transparent cells are rejected but intentional tinted cells are allowed; at least one visible cell border is required because outer wrapper/last-row rules remove selected edges; shared group guidance and checkbox captions do not follow the individual-field rule; explicit ellipsis/line-clamp is allowed (subsidy summary previews); `object-fit:cover` is an intentional image crop; remote image loading is outside this offline test. Numeric token checking targets numeric-only cells to avoid claiming arbitrary prose parsing. Pure numbers without units and collisions between arbitrary positioned containers still need visual review.

`test_layout_mutations` renders independent healthy/broken HTML fixtures with the real stylesheet at both widths: 22 broken cases, plus positive controls for local scrolling and quantitative bars. It does not mutate production HTML. Generator checks fail when a new page has not received the shared markup.

## Authoring

Run `node tools/gen_layout_markup.mjs` after adding/changing pages. It preserves wording and JSON-LD while moving help, associating `aria-describedby`, marking FAQ h3+p, keeping numeric tokens together, wrapping plain tables, aligning explicitly numeric headings, and adding TOCs to calculators with three or more h2 sections. Existing article TOCs are owned by their existing generator. Hubs, short tools and embeds do not need a reading TOC. Help for one control goes below it; group instructions may precede a group. Dynamic form builders must follow the same markup themselves. Embeds include `/assets/embed-layout.css`.

Use `.fee-pair.field-pair` for simple paired fields and `.field-inline-help` for a short control beside its label with a full-width help row. Tables in main receive the common borders/background; `.num` means right-aligned tabular values, `.numeric-token` prevents a number and unit splitting. FAQ questions and answers receive `.faq-question`/`.faq-answer`; original Q./A. prefixes are retained in `.faq-existing-marker` to avoid duplicate visible markers. Never change FAQPage to match a purely visual change. Do not add article-local style blocks.

## Representative image comparison

`visual-pages.json` has 16 representatives/components × two widths. `test_layout_visual` compares PNGs to committed baselines. A dimension change or more than 1% pixels with RGB channel delta >32 fails and writes expected/actual/diff files under `.layout-artifacts/`. The comparator includes a synthetic large-change rejection and identical-image acceptance check. This is a useful large-change alarm, not proof of visual quality: one-pixel defects or changes outside the representative crops can remain below threshold. All-page geometry covers the broader site.

Clock: 2026-09-27 JST, reduced motion, locale ja-JP, timezone Asia/Tokyo, DPR 1. Component crops hide only the sticky site header to prevent it covering the target; full viewport images retain it. External requests are blocked consistently. Baselines record OS/architecture/Playwright/Chromium versions and require an exact environment match; rendering on a different OS/font stack must not silently pass.

For an intentional UI change: run the tests, open expected/actual/diff at both widths, inspect the affected full page and SVGs, record the review, then run `node tests/test_layout_visual.mjs --update` and commit the reviewed PNGs with the implementation. This explicit command is never invoked by the test runner. On browser/OS/font migration, use the old recorded environment to establish the old result, review all regenerated images on the new environment, then explicitly update metadata and baselines in a dedicated reviewed change. Fonts come from the OS stack, so install/update fonts only with this review. Merely changing metadata is not an acceptable migration.

After changes, inspect the target area **and** top/TOC, input pairs, tables, diagrams, FAQ, footer at 1280 and390; inspect PR-bearing pages without changing PR/AdSense. Keep paths to before/after screenshots. `scrollWidth` alone is insufficient. Never edit the worktree while the full test runner is running: existing mutation tests temporarily modify documents and restore them.

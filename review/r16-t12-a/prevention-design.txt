# 統合設計（2026-09-29 19:0x JST）

## 両案が一致した事実（実測）
- 対象: 確定 high 106所見（r9 17・r10 24・r11 29・t1 24・t2 2・t3 2・t4 4・b1 4）。延べ件数で、同一原因の重複を含む。
- **毎回新しい high が出る主因は「見る範囲が周ごとに作り直され、広がらない」こと**。sol は1ページ約20主張で止まる（Opus 実測 18.2〜20.7件/ページ）が、数字・言い切りを含む文は1ページ中央値153文（上位120ページで 18,745文）。
- **今の守りの穴**: ①high の元の文の約半分（Opus: 97件中49件）は数字も言い切り語も含まない＝check_claims の網に入らない（条件・対象者・区分の取り違え＝Astra の S・K 型 46/106）。②約4割（Opus 42件、Astra U 型 26）は計算機の中身と画面（初期値・入力欄・対象外表示）にあり、法が答えを変える条件に入力欄も対象外表示も無いものが多い。
- 工程: Opus は git blame で 90/106（85%）が初回執筆・初回実装、レビュー修正で入ったのは2件と推定。Astra は確定できたのは22件で残り84件は未特定と慎重。→ **「初回に入って、周回が拾い切れていない」**で両案は矛盾しない。
- 司令塔の取りこぼし（執筆便の未コミット新規記事 denchoho-scanner-hozon が止まっていた）も両案が指摘。

## 採用する仕組み
### 執筆時
- **W1 正本を先に読む**（write.md 手順2）: 登録済みテーマなら source_registry の固定正本を先に読み、台帳の source と corpus_ref はそこから。テーマ外なら「該当テーマなし」と書き、使った一次資料を registry 形式で RUN に最小登録。
- **W2 文単位の台帳（中心）**: 新しいスクリプトがページの確認単位（title・meta/OG・見出し・p・li・表のセル・SVG text・FAQ・ラベル/選択肢/初期値）を機械で列挙し、各単位を「台帳の主張 ID に結びつける」か「非主張（理由つき）」に振り分けさせる。**LLM が台帳から逆算して単位を作らない**。まず警告モード（run_tests を赤にしない）、新規記事だけ強制。文面の機械的な変更（太字・空白）で ID が揺れないよう正規化。
- **W3 公開前の独立照合**: 執筆便の差分（新規記事は全体、改稿は変えた単位＋同じ主張の全出現）を sol が単位ごとに照合し、Astra が審査してから司令塔の検品へ。theme_round に未コミットの作業場を読み取り専用で渡す入力を足す。
- **W4 計算機の条件表**: core ごとに「法が答えを変える条件」を列挙し、各条件を **入力欄／固定（前提として明示）／対象外（計算を止める or 明示）** のどれかに対応させ、境界値ケースと結ぶ。検査で強制（pending は減らすだけ）。HTML の実際の初期値でも計算させる。
- **W6 受け渡し**: 執筆便の終わりに、rc・result.md・コミット実在・未コミット差分なし・プレースホルダ残りなしを機械で確かめ、満たさなければ block 通知（未コミットの下書きも在庫に数える）。満たせば review-receipt.json（検査対象の SHA・範囲・未処理単位 0・範囲内の未解決 high 0）を置き、司令塔が受領する。

### レビュー時
- **R1 周を「抜き取り」から「未照合の残りを減らす」へ**: theme_round に単位モードを足し、coverage.json（単位総数・確認済み・非主張・未処理、単位→主張 ID）を出す。未処理が残る束・未知の ID・判定の抜けは Astra に進ませない。1束は20〜40単位で切る。
- **R2 条件表の周（b2）**: pending 11 core と high の出た core から条件表を作る。
- **R3 審査者の誤りも数える**: 不採用・昇格/降格を記録し、ok の抜取（1周30件）で見逃し率を出す。横展開は topic と rg。
- 正本外（out_of_corpus）は誤りとせず「必要な正本」を付けて次のテーマ周へ送る。

### 指標（日報に数行）
- 被覆率（確認済み単位／列挙単位）: 上位120ページで100%を 2026-11-30 まで。**100% は正確性の保証ではない**と明記。
- 新フローを通った公開の30日内 high 逃逸: 0件目標（1件でも原因分析）。
- 新規記事の初回 high 率: 最初の10本で基準、次の10本で半減。
- 確認済みの文から後で high が出る率: 1%未満（少数標本では宣言しない）。
- 条件表が揃った計算機: 全 core を 2026-11-15 まで。
- 運用接続: 未コミットの公開依頼 0、24時間超の未受領 0。

### やらないこと
- 新しい launchd・状態機械・Mac 全体ロック・DB・オントロジー。在庫全ページを一度に関門化（公開が止まる）。語の存在だけで落とす検査。検品（司令塔）を外すこと。資格法の線（INQUIRY_POLICY）を越える個別判断の文。

## 実装の段階（Astra に依頼）
- **段階0（今日）**: W1（write.md）、W6（write.sh の完了検査と block 通知・receipt）、high の起源の記録（high_origin）。
- **段階1**: W2 の単位列挙と警告モード（`tools/segment_claims.mjs`＋`check_claims.mjs --segments`、`SEGMENTS_STRICT=1` で関門）＋ 被覆の報告（coverage_report）。新規記事は強制。
- **段階2**: W4 条件表の検査（`tests/conditions/*.json`＋`test_condition_tables.mjs`、`_status.json` の pending は減らすだけ）。high の出た core から登録。
- **段階3**: R1 の単位モード（theme_round `--segments`・`--draft-worktree`）と W3 の接続。
- 段階4（継続）: 上位120ページを単位モードで一巡、条件表の全 core 化、SEGMENTS_STRICT を変えた行の関門へ。
